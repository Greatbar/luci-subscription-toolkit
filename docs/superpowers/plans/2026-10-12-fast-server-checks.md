# Ускорение массовых проверок LuCI Subscription Toolkit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Выполнение основным агентом, без субагентов.

**Goal:** Максимально сократить время проверки 11 серверов на AX6S, сохранив независимые результаты задержки, скорости и доступности Telegram Web; установить проверенные изменения на роутер.

**Architecture:** Один запрос LuCI запускает одно массовое задание под существующим mutex. Один временный sing-box обслуживает принятые профили через отдельные локальные inbound-порты с явным соответствием inbound → outbound. Лёгкие проверки выполняются параллельно; измерения скорости переиспользуют тот же процесс и выполняются без искусственных пауз, последовательно для сохранения сопоставимости результатов.

**Tech Stack:** LuCI JavaScript, ucode, BusyBox shell, curl, sing-box 1.14.2, OpenWrt на AX6S.

**Spec:** Исходное задание пользователя в текущем диалоге; технические решения и критерии ниже.

## Global Constraints

- Без субагентов, commit/push, обновления зависимостей и постороннего рефакторинга.
- Не менять MAIN, выбранный сервер, маршрутизацию, подписку и пользовательские настройки ради измерений.
- Сохранить mutex, проверки принятого состояния, ограничение трафика и защиту от повторных speed-проверок одного ID.
- Полностью скачанные 4 МиБ за положительное время менее 0,5 с дают числовой результат с отметкой короткой выборки.
- Задержка, скорость и Telegram Web сохраняются отдельно; отказ одного теста не отменяет остальные.
- Минимальная проверка работоспособности; без полного integration/recovery/audit-прогона и отчётов с хеш-суммами.
- Установка на роутер уже разрешена пользователем. Сохранить предыдущие изменяемые файлы для обратной установки.

## Проверенные основания и выбранное решение

- `dashboard.js:runTests` последовательно перебирает серверы и виды проверок, опрашивает status перед каждой пробой и ожидает её подтверждения с интервалом 500 мс.
- `backend.uc:get_through` запускает и останавливает временный sing-box для каждого speed/service-запроса; `start_probe` дополнительно запускает `sing-box check`.
- Готовность и остановка временного процесса проверяются с `sleep 1`: возможны лишние секунды на каждую пробу.
- `model.uc:sample` отвергает любой результат с длительностью тела менее 0,5 с, включая полную загрузку заданного объёма.
- Массовый backend предпочтительнее параллельных одиночных RPC: последние конкурируют за общий mutex и каталог job.
- Постоянный диагностический daemon не нужен: один временный процесс на задание даёт переиспользование без нового жизненного цикла сервиса.
- Начальный предел лёгких проб — 8 одновременно. Speed — 1: одновременные загрузки делят WAN и CPU, меняя смысл показателя. Их запуск не ждёт cooldown других серверов.
- 10–15 с для восьми серверов — ориентир для лёгких проверок, не подтверждённое обещание для полного набора со speed. Реальное время всех 11 серверов измерить один раз после установки.

## Review Focus

1. Быстрая полная загрузка и короткая частичная загрузка различаются; нулевое время и превышение cap остаются ошибками.
2. Таймаут/отказ одного сервера не задерживает свободные слоты и не затирает успешные показатели других видов.
3. Отмена прекращает выдачу новых проб, дожидается ограниченных активных проб и убирает временный sing-box.
4. Задание cron и конфликт mutex не выдаются за успешно начатую массовую проверку; прогресс относится к конкретному запросу.
5. Неизвестные/повторные ID, изменившийся лимит трафика и повторный speed cooldown обрабатываются без скрытого дополнительного трафика.

## Task 2: Единое массовое задание и временный sing-box

**Files:** `root/usr/libexec/podkop-tools/backend.uc`, `root/usr/libexec/podkop-tools/task`, `root/usr/libexec/rpcd/podkop-tools`, `root/usr/share/rpcd/acl.d/luci-app-subscription-toolkit.json`; при необходимости создать `root/usr/libexec/podkop-tools/probe-worker` и включить его в существующий список payload.

**Interfaces:** RPC `batch({ids: string[], kinds: string[], speed_bytes: integer, token: string})`; RPC `cancel({token: string})`. Разрешённые виды: `latency`, `service`, `speed`; ID — 64 hex, максимум 128 уникальных ID. Status возвращает `batch: {token, state, done, total, error}`, где state — `running|finished|cancelled|failed`. Существующие одиночные RPC остаются совместимыми.

- [x] Проверить на роутере наличие параллельного `xargs -P` и способ короткого ожидания без зависимости от дробного BusyBox sleep; выбрать доступные штатные средства.
- [x] Проверять входные ID, виды, token и подтверждённый `speed_bytes` до сетевого трафика. Под mutex сверить принятое состояние и ресурсы роутера один раз на пакет.
- [x] Создать одну конфигурацию sing-box: отдельные loopback mixed-inbound, один VLESS outbound на ID, явные route rules, bootstrap DNS и существующий bypass mark. Исключить detour/подмену через MAIN.
- [x] Проверить конфигурацию один раз и запустить sing-box один раз. Заменить секундные опросы готовности/остановки ограниченным коротким ожиданием; не удалять job, пока принадлежащие ему процессы ещё используют файлы.
- [x] Организовать общую очередь лёгких проб с 8 слотами без ожидания самого медленного ранее запущенного сервера. Пробы используют отдельные приватные curl-конфиги и файлы результата.
- [x] Задержку измерять через каждый профиль на существующий health URL; принимать только успешный HTTP 204. Telegram Web проверять по существующему TLS/HTTP/MIME/markers-контракту.

- [x] Отмена по token останавливает очередь данного задания; активные curl ограничены timeout. Cleanup обрабатывает обычное завершение, исключение и сигнал, не затрагивая штатный sing-box.
