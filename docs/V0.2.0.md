# Historical v0.2: v0.2.0-r2

This release extends the existing Podkop Tools job/Selector/recovery mechanism. It
adds no routing controller or persistent process. Supported topology is one
`main` VLESS Selector, additional Podkop `Exclusion` sections and an optional
explicitly bound `antigravity` Proxy section. Other Proxy/VPN/Block sections are
rejected. The default installation creates no Antigravity section. Generation, apply and rollback retain
exclusion routing and DNS semantics and independent firewall rules.

Compared with r1, r2 includes the deployed scheduler, optional stable-ID-bound
Antigravity route and clock-jump fix. Clock drift uses explicit signed comparisons
rather than an unavailable `abs()` builtin. No local init fingerprint, router
configuration or private subscription data is part of this release.

## Monitoring and recovery

The v0.2 package migration replaces the old health schedule with one minute cron;
it preserves automation enabled/disabled and subscription apply policy. Normal
health checks the active outbound and one reserve using the existing sing-box
Clash API, with a 5-second per-probe timeout and a shared monotonic 15-second
budget (including API calls). There is no speed test or extra sing-box process
in normal monitoring. Busy/missed/API-error samples are unknown, not failures.

Scheduled `check`/`fetch` and `due` reserve priority and wait up to 90 seconds
(monotonic) for the existing job lock. Health yields to a live waiting owner.
Overlapping check/fetch calls share one reservation; duplicate due calls also
coalesce. Operations remain serialized by the original lock. This does not retry
a completed fetch or apply. A wait timeout is explicit, not an unreported loss.
Short private receipts are retained only in `/tmp/podkop-tools/scheduler/`:
48 JSON files per family (`fetch-*.json`, `due-*.json`). They include queued/start/
finish times, wait/runtime, exit code, result/reason and safe apply/fetch status.
Policy skips, duplicates, interrupted waits and lock timeouts remain auditable
without the system ring buffer. Reboot clears these tmpfs receipts.

Three failed observations over at least 120 seconds trigger strict HTTP204
confirmation. Recovery first fetches the subscription, then tests a rotated
profile of the same stable ID, then reserves in configured order. A pass has
45 seconds shared budget: confirmation up to5s, fetch up to15s, candidate search
up to20s and5s bookkeeping. Search progress is held in RAM, so later passes do
not start again with fetch or the first unreachable reserves. Ongoing failures
allow another pass each minute; subscription retries are at most every5minutes.
A working reserve permits subscription refresh every15minutes.

The search deadline never interrupts an already started durable apply/rollback.
Those operations retain the existing finite transaction timeouts and may take
longer than45seconds, including native Podkop reload/list-update lock waits.
Existing-profile failover uses the Selector API without restart.

The user-selected preferred ID is separate from the active ID and own switch
intent. External Selector changes observed at runtime are adopted as manual
preferences. At boot, own intent is reconciled first; an unexplained valid live
choice is adopted without forcing the old stored choice. If Podkop itself lost
an unobserved external choice at sudden power loss, the toolkit cannot recover
that intention. State IDs and subscription ownership checks are not reset.

Reserves follow `priority_ids`; unlisted IDs follow subscription order. The
preferred server gets the reserve probe slot every5minutes while on reserve.
Return requires3 successful samples spanning10minutes and a fresh strict check.
Latency switching defaults OFF. When enabled, the default trigger is1000ms
sustained5minutes; fresh active/candidate tests must show improvement of both20%
and50ms, and the candidate must be20% below the threshold. The non-emergency
cooldown is10minutes with at most3 transitions per30minutes. Confirmed outages
bypass these limits; no rate limit prevents using a fourth working server.

Control HTTPS reachability and delay do not certify YouTube, ChatGPT, Discord
Voice, UDP applications or the usefulness of a server for all services.

## History and interface

Statistics are sparse hourly numeric aggregates keyed by stable identity, with
sample attempts/successes, latency sum/min/max, confirmed outages and switches.
Availability is successes / actual recorded attempts. Missing time is not uptime.
LuCI shows24h/7d/30d windows with visible gaps and lazy SVG charts, no external
chart library. Statistics RPC is read-only and contains no connection secrets.

History lives in tmpfs, capped at1MiB serialized data and720hours. A compressed
atomic snapshot is at most256KiB and written no more than once in6hours. Excess
old intervals are discarded and coverage is marked truncated. Snapshot compression
and restore are separate finite maintenance work with an independent nonblocking
history lock. If it is busy, statistics are best effort; server recovery proceeds.
Detailed per-probe logs are not stored. Crash may lose the last6hours of statistics.
The extra peak RSS acceptance limit for history processing is8MiB; capacity is
measured with real64-character IDs rather than short fixture labels.

Implementation compatibility checks use a boot-scoped metadata cache during normal
monitoring, invalidated on manifest/file changes. Full SHA256/version validation
is retained before mutations. Runtime is parsed once per job and invalidated
following native reload. No verification is bypassed by the cache.

## Validation and delivery

### Optional Antigravity route

In addition to MAIN and Exclusion sections, the backend and native staging allow
exactly one Proxy section named `antigravity`, using `proxy_config_type outbound`.
Its `subscription_node_id` must identify an accepted subscription node. Configure
the section's standard Podkop `outbound_json`, domain list and Mixed Proxy port
(for example LAN port2081); keep MAIN on2080. Restrict access using the LAN
listener and firewall. Place the AG domain rule before overlapping MAIN lists.

Selection/preference/failover still control MAIN only. Fetch stages the bound AG
profile from the candidate; apply and recovery update it in the same native UCI
transaction. Rollback restores the bound profile from the rollback nodes while
retaining the latest AG domains/port and Exclusions. Missing bound IDs and profile
drift fail closed. Other additional Proxy/VPN/Block sections remain unsupported.
The MAIN accepted-state schema and public stock-init compatibility hashes are
unchanged. `tests/podkop-tools/antigravity.py` contains the focused fixture suite
selected with `integration.py --antigravity` in the existing isolated OpenWrt lab.

For focused r2 validation run `python3 -B tests/run.py antigravity` in a clean
manifest-only candidate checkout. It includes the one-MAIN and clock-jump
regressions; native generation/API/DNS/rollback are real, while provider HTTPS
and control-health responses in this optional-route fixture are synthetic.
The fixture installs the built APK and does not copy over its backend.

Run `python3 -B tests/run.py all` for the complete matrix in a clean manifest-only candidate checkout.
The root checkout may contain ignored private backups; never copy those into the
candidate, weaken the audit, or move them for packaging. Build from an immutable
candidate snapshot, and run prepublish and reproducibility checks. No commit,
push, publishing or router installation is implied by local preparation.

The test report records userspace results separately from hardware evidence.
An actual weak-router15-second claim requires hardware timing; Docker cannot
certify CPU, Wi-Fi, hardware dataplane or flash wear.
